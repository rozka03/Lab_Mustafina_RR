# Червь Shai-Hulud в npm


## Что произошло?

Атака началась 4 августа после взлома GitHub-аккаунта разработчика Джареда Рэя, который поддерживает библиотеку keyv и несколько популярных инструментов кеширования. Злоумышленники добавили вредоносные файлы прямо в основную ветку проектов, после чего выпустили новые версии через штатный механизм GitHub Actions. Вредоносная программа искала токены npm и GitHub, ключи AWS, секреты Kubernetes, учётные данные Docker, токены HashiCorp Vault, Slack и Stripe. Украденные токены позволяли червю публиковать заражённые версии пакетов от имени новых разработчиков. Так атака переходила с одного проекта на другой без ручного взлома каждого аккаунта.



## Компания и сервис

Червь был загружен в npm-пакеты в **GitHub**, который принадлежит компании **Microsoft**.



## Классы уязвимости

Основной класс по актуальному **OWASP** Top 10:

*OWASP A03:2025* — **Software Supply Chain Failures**, то есть отказ или компрометация цепочки поставок программного обеспечения.

OWASP прямо приводит Shai-Hulud как пример самораспространяющегося npm-червя, который внедрялся через заражённые версии пакетов, выполнялся через post-install, крал секреты и автоматически публиковал новые вредоносные версии.

По Common Weakness Enumeration (**CWE**) червь Shai-Hulud можно отнести к нескольким классам:

*CWE-399*: Uncontrolled Resource Consumption — червь потребляет значительные ресурсы системы (CPU, память, дисковый ввод-вывод) в процессе работы.
*CWE-500*: Exposure of Credential (in this case, via postinstall hook) — кража токенов и ключей происходит через автоматически выполняемый при установке хук (postinstall), что раскрывает конфиденциальные данные.
*CWE-602*: Improper Input Validation — входные параметры обрабатываются без должной проверки, что позволяет внедрить вредоносный код.

Прямого совпадения с конкретной **CVE**-номером у Shai-Hulud нет, так как это не классическая уязвимость в коде, а вредоносная программа.



## Как обнаружили

Первые заражённые версии были замечены исследователями после публикации вредоносных npm-релизов примерно 15 сентября 2025 года. Исследователи обратили внимание на необычные postinstall-скрипты, кражу секретов и появление публичных GitHub-репозиториев с названием Shai-Hulud.

*Также были обнаружены:*

- новые версии популярных пакетов без ожидаемых изменений;
- добавление lifecycle-скриптов в package.json;
- обращения npm-пакетов к GitHub API;
- создание публичных репозиториев с одинаковым названием или описанием;
- публикация новых версий пакетов вскоре после компрометации maintainer’а;
- неожиданные npm-публикации из CI или с рабочих станций;
- использование украденных GitHub, npm и облачных токенов.

Масштаб быстро уточнялся. В первых сообщениях фигурировало более 180 заражённых пакетов, а CISA позднее указала на более чем 500 скомпрометированных пакетов до блокировки распространения.



## Подтверждённый ущерб

- Заражено более 500 пакетов или пакетных версий по оценке CISA/GitHub.
- Украдены GitHub PAT, npm-токены, AWS-, GCP- и Azure-ключи.
- Украденные секреты публиковались в публичных GitHub-репозиториях.
- Скомпрометированные токены использовались для дальнейшей публикации вредоносных npm-версий.
- Потенциально были затронуты рабочие станции разработчиков, CI/CD-runner’ы и проекты, устанавливавшие заражённые версии.

Подтверждённого общего числа украденных записей или файлов публично не установлено.



## Что сделали после

GitHub и npm:

- удалили более 500 скомпрометированных пакетов;
- начали блокировать загрузку пакетов, содержащих известные IoC вредоносной кампании;
- объявили ужесточение требований к публикации;
- начали выводить из эксплуатации классические npm-токены;
- стали ограничивать срок жизни granular tokens с правом публикации;
- продвигали trusted publishing и публикацию с обязательной защищённой аутентификацией;
- рекомендовали переход от TOTP к phishing-resistant FIDO-аутентификации.



## Что должно было быть сделано до

Меры превентивной защиты:

1. Ограничение токенов:

- Использовать токены с минимальными привилегиями и коротким сроком жизни
- Внедрить OIDC (OpenID Connect) trusted publishing вместо долгоживущих npm-токенов

2. Отключение lifecycle скриптов:

- Использовать npm install --ignore-scripts для зависимостей
- Сделать выполнение скриптов опциональным

3. Контроль зависимостей:

- Пиннинг версий.
- Внедрение "пакета остывания" — не устанавливать свежие версии сразу

4. Сегментация CI/CD:

- Разделять джобы на установку зависимостей и публикацию, чтобы токены публикации не были доступны на этапе установки

5. Мониторинг и обнаружение:

- Отслеживать исходящий трафик из CI
- Сканировать зависимости на наличие известных вредоносных пакетов (например, через OpenSSF Malicious Packages feed)
- Мониторить неожиданные события: создание публичных репозиториев, публикации пакетов вне расписания 



## На каком этапе жизненного цикла разработки (SDLC) можно было поймать

1. Разработка/Сборка:

- SAST/DAST: Сканирование кода на наличие вредоносных скриптов в package.json и binding.gyp
- SCA (Software Composition Analysis): Проверка зависимостей по базам известных вредоносных пакетов перед установкой .
- Политика зависимостей: Блокировка установки пакетов с postinstall или требование ручного approval

2. CI/CD (Непрерывная интеграция/Непрерывное развертывание):

- Контроль окружения: В CI джобах для установки зависимостей не должно быть NPM_TOKEN с правами на публикацию
- Изоляция: Выполнение установки в изолированных средах с ограниченным сетевым доступом (egress filtering)

3. Тестирование:

- Динамический анализ: Запуск приложения в песочнице с мониторингом сетевых подключений и доступа к файловой системе
- Canary тесты: Установка тестового пакета с postinstall, который проверяет, запускаются ли скрипты изолированно

4. Эксплуатация:

- Runtime protection: Использование инструментов защиты на этапе выполнения для детекции аномального поведения (обращение к Ethereum RPC, создание репозиториев) 



## ОТВЕТЫ НА ВОПРОСЫ

1. Чем угроза отличается от уязвимости, а уязвимость — от риска?
**Угроза (threat)** — потенциальное нежелательное событие: «кража базы клиентов». Существует всегда, независимо от нашего кода.
**Уязвимость (vulnerability)** — конкретный дефект в нашей системе, который позволяет угрозе реализоваться: та самая склейка строки в SQL.
**Риск** — ожидаемый ущерб: вероятность реализации × размер ущерба. Управляют именно риском: его можно **снизить** (исправить), **передать** (страховка, аутсорс), **избежать** (убрать функциональность) или **принять** (осознанно жить с ним).

2. Почему валидация на JavaScript не является защитой? 
Клиент полностью под контролем злоумышленника. Запрос можно отправить из curl или Postman, минуя браузерный JS. Защита есть только на сервере.

3. В чём разница между аутентификацией и авторизацией? Какая из них чаще ломается и почему? 
**Аутентификация** — «кто ты». Проверка сессии: пользователь вошёл, это Иванов. Эта проверка была.
**Авторизация** — «что тебе можно». Проверка, что запрошенный объект принадлежит именно этому пользователю. Этой проверки не было вообще.
Ломается чаще вторизация 

4. Почему в примере из раздела 1.3 не помогло бы экранирование кавычек? 
Потому что в примере параметр user_id вообще не был заключён в кавычки в SQL-запросе. Экранирование кавычек защищает только строковые параметры (обёрнутые в '). Здесь же злоумышленник вставляет 1 OR 1=1 в числовое поле, и кавычек для экранирования просто нет.

5. Объясните, почему параметризованный запрос защищает от инъекции, а фильтрация слова `OR` — нет.
Фильтрация обходится регистром, кодированием, комментариями.
Параметризация - это данные и запрос передаются отдельно. Строка '1 OR 1=1' становится значением, а не кодом.

6. Почему хранимая XSS опаснее отражённой? 
Хранимая XSS лежит на базе, и если жертва просто откроет, то все нужные данные придут злоумышленнику. При отражённой XSS вредителю необходимо заманить жертву по специальной ссылке.

7. Почему `CVE` нельзя использовать вместо `CWE` и наоборот?
**CWE (Common Weakness Enumeration)** — каталог типов слабостей, «класс болезни».
**CVE (Common Vulnerabilities and Exposures)** — идентификатор конкретной уязвимости в конкретном продукте, «диагноз пациента».

8. Что означает принцип полного посредничества и какую категорию OWASP нарушает его несоблюдение? 
Полное посредничество (complete mediation). Каждое обращение к каждому объекту проверяется **каждый раз**. Не «проверили при входе в раздел, дальше доверяем». Решение об авторизации не кэшируется. 
Нарушение этого принципа и даёт уязвимость №1 в мире — Broken Access Control.

9. Почему хеширование паролей через SHA-256 считается неправильным, если сама SHA-256 стойкая?
SHA-256 - это быстрая хеш-функция, она создана для проверки целостности данных. Для хранения паролей нужна намеренно медленная и ресурсоёмкая функция, которая усложняет перебор

10. Приведите пример дефекта проектирования (flaw), который нельзя исправить патчем.
Восстановление пароля по секретному вопросу «девичья фамилия матери». Код для этого вопроса может быть написан идеально и без багов, но сама архитектура (идея) небезопасна, потому что эту информацию легко узнать или подобрать. Единственное исправление — полная переделка механизма восстановления доступа.

11. Какие две категории появились в OWASP Top 10:2025 и почему? 
**A03 Software Supply Chain Failures** — расширение прежней «Vulnerable and Outdated Components» (A06:2021). Теперь это не только «старая библиотека», но весь конвейер: репозитории, сборка, CI/CD, механизм доставки обновлений. Причина повышения — SolarWinds, Log4Shell, червь **Shai-Hulud** в npm (2025, более 500 пакетов, кража токенов разработчиков), атака на кошелёк Bybit (2025, ущерб около 1,5 млрд долларов).
**A10 Mishandling of Exceptional Conditions** — полностью новая: ошибки обработки исключений, «fail open», отсутствие отката транзакции, утечка деталей в сообщениях об ошибке.

12. Что такое «fail open» и чем он опасен? 
Fail open (отказ с открытием) — это ошибка, когда при возникновении исключения или ошибки в работе механизма безопасности, система разрешает доступ вместо того, чтобы запретить его.
Антипаттерн в коде, когда в блоке try-except при ошибке проверки прав пользователю присваиваются права администратора (is_admin = True). Это может привести к полной компрометации системы.

13. Зачем нужен SBOM? 
SBOM (Software Bill of Materials) — это машиночитаемый перечень компонентов программного продукта: библиотек, зависимостей, их версий и, в зависимости от формата, отношений между ними.
Он нужен, чтобы быстро определить, затронут ли продукт конкретной CVE; выявить транзитивные зависимости, которые разработчик напрямую не добавлял; ускорить реагирование на инциденты в цепочке поставок; сопоставить компоненты с результатами SCA-сканеров; контролировать лицензии и происхождение зависимостей; понимать состав конкретного сборочного артефакта, а не только исходного репозитория.

14. Почему CVSS 9.8 не всегда опаснее CVSS 5.0? 
CVSS - техническая серьёзность, а не риск. Дыра с 9.8 в тестовом приложении менее опасна, чем дыра с 5.0 в платёжном шлюзе.
